## 一个让人不适的演示

我在做健康管理类应用的时候试过一个很自然的想法：用户说「今天早餐吃了两个鸡蛋、一杯牛奶」，直接丢给大模型，让它返回总热量。

演示效果非常好。然后我换了个说法再问一次：

```text
「今天早餐吃了两个鸡蛋、一杯牛奶」
→ 总热量 245 kcal

「早餐两个鸡蛋加一杯牛奶」
→ 总热量 270 kcal
```

同一个问题，换个语序，答案差了 25 kcal。

这在聊天场景里无所谓，反正就是聊天。但如果用户拿这个数字去判断今天还能不能吃晚饭、要不要加练，那**这个产品就是不可用的**。

问题不在于模型能力不够，而在于我让它干了它天生不擅长的事。

## 分工：AI 负责理解，程序负责计算

后来我把架构整个拆成两半：

| 能力 | 由谁完成 | 为什么 |
| --- | --- | --- |
| 理解自然语言 | ✅ AI | 这是它唯一无可替代的能力 |
| 图片识别食物 | ✅ AI | 同上 |
| 生成个性化建议 | ✅ AI | 需要结合上下文表达 |
| 连续对话 | ✅ AI | 同上 |
| **热量计算** | ❌ 程序 | 同一输入必须永远得到同一输出 |
| **BMI / TDEE 计算** | ❌ 程序 | 公式是确定的，交给模型就是引入不确定性 |
| **营养统计** | ❌ 程序 | 需要可追溯、可复算 |
| **数据持久化** | ❌ 程序 | 模型不碰数据库 |

一句话总结这条线：

> **AI 是分析师，不是计算器。**

## 落地的关键：结构化输出

拆分完之后，两个角色之间需要一个**契约**。我的做法是：让模型只输出 JSON，业务层负责一切计算。

用户输入：

```text
今天早餐吃了两个鸡蛋、一杯牛奶
```

模型返回（注意它**没有**返回热量）：

```json
{
  "meal": "breakfast",
  "items": [
    { "name": "鸡蛋", "quantity": 2, "unit": "个", "confidence": 0.95 },
    { "name": "牛奶", "quantity": 1, "unit": "杯", "confidence": 0.88 }
  ]
}
```

剩下的事交给程序：

```java
// 伪代码：标准食品库 + 确定性计算
List<FoodItem> matched = foodRepo.match(parsed.getItems());   // 命中标准食品库
NutrientResult r = calculator.calculate(matched);             // 纯函数，可单测
dailyStat = statsService.accumulate(userId, r);               // 落库
```

这个拆法带来三个好处：

**1. 可测试。** `calculator.calculate()` 是个纯函数，给定输入必有输出，单元测试直接断言。而「模型今天心情如何」不需要进测试用例。

**2. 可追溯。** 每一千卡都能顺着链路回溯：这条饮食记录 → 匹配到食品库里的哪一条 → 每 100g 多少热量 → 乘以多少克。用户质疑数据时能解释清楚，这比一个黑盒数字重要得多。

**3. 模型可替换。** 想从 A 模型换成 B 模型？只需要保证 JSON 契约不变。业务层的计算逻辑一行都不用动。

顺带还解决了一个成本问题：**无外部 API Key 时，整套系统用内置词典的 Mock 实现照样能跑**——因为核心链路（计算、统计、存储）本来就不依赖模型。

## 两个容易忽略的设计原则

### 原则一：AI 的输出必须是结构化数据

不要接受「模型返回一段自然语言，然后用正则去抠数字」。它会以你想象不到的方式失败：数字写成中文、单位漏掉、多返回值、加个括号补充说明……

强制 JSON 输出，再用 JSON Schema 校验。校验不通过就重试或者降级，**绝不让脏数据进业务层**。

### 原则二：把「解释」和「事实」分开存

- 事实（热量、蛋白质克数、步数）→ 数据库，可复算，可审计。
- 解释（「你这周蛋白质偏低，建议增加鸡蛋和豆制品」）→ 可以生成后存快照，因为它本来就是一次性的表述。

如果哪天发现解释生成得不好，重新生成一遍就行，不会影响任何统计结果。

## 那 AI 到底强在哪

拆掉计算之后，AI 的价值反而更清楚了。它能做的事是这些：

- **降低记录门槛。** 用户说一句话、拍一张照片就能完成记录，不用在食品库里翻五分钟。
- **跨越数据做归因。** 「你这周三到周五热量都超标，但运动量没变，可能是外卖比例上升了」——这种事情规则引擎写起来很痛苦，模型很擅长。
- **调整表达方式。** 同一条建议，给健身的人可以说「蛋白质缺口 30g」，给普通用户应该说「多吃一个鸡蛋」。
- **持续陪伴。** 结合历史做连续对话，这是传统「记录工具」做不到的。

## 小结

这次重构给我的最大启发是：**不要因为模型能回答某个问题，就让它来负责那个问题。**

判断标准很朴素——**这个输出需要每次都一样吗？** 需要，就交给程序；不需要，才交给模型。把这条线划清楚，系统的稳定性、可测试性、可替换性都会跟着上一个台阶。
