不知道大伙儿有没有过这种体验——面试官问「B+ 树插入的时候，节点具体是怎么分裂的」，你脑子里立刻弹出那句背烂了的话：「满了就分裂，把中间那个键提到父节点」。

然后面试官接着问：「提上去之后，原来那个节点里还有没有这个键？」

当场裂开。 (꒦ິ⌓꒦ີ)

我上次就是这么裂开的。回来之后越想越不服气——这玩意儿明明就四条规则，怎么就背成了玄学？于是我干脆把整棵树搬进浏览器，做了个能自己插数据的沙盒：你输一个数字，看着它从叶子一路长上去，每一步到底动了谁、哪个键复制了、哪个键被搬走了，全都写在旁边的日志里。

今天咱就把这件事从头到尾盘一遍。看完你会发现：**分裂根本不是一件事，而是两件完全不同的事**，而大多数资料把这两件事糊成了一件。

---

## 一、先整明白 B+ 树到底长啥样

大白话定义：**B+ 树就是一个「真东西只放叶子层，上面几层全是路牌」的多叉搜索树。**

打个图书馆的比方。你进大厅先看指示牌：「30 号以前的往左走，30 号以后的往右走」。牌子上写的那个 30，是书架上的一本真书吗？

不是，它只是一块牌子。

B+ 树一模一样：

- **叶子层** = 书架，书（键 + 数据行）真真切切在这一层
- **上面几层** = 大厅指示牌，只有键，一个字节的真实数据都没有
- **叶子之间** = 还拉了根绳子把书架按顺序串起来，你要「30 到 50 之间所有的书」时，顺着摸过去就行，不用回大厅重新问路

这里有个细节特别重要，后面所有的「复制还是搬走」都是它推出来的：

> 路牌上的数字，是从叶子那儿**抄**过来的。抄的时候原书还在书架上没动，所以牌子和书可以同时存在一份。

记住这句话，第二章马上要用。

顺便把规矩交代清楚。咱用 4 阶 B+ 树举例（每个节点最多 4 个孩子，也就是最多 3 个键），因为阶数小，图上看得清。真实 MySQL 里一个页 16KB，能塞几百个键，但规则一毛一样。

## 二、插一个数据，先看最普通的情况

先讲最常见的那种，因为**绝大多数插入其实什么都没发生**。

叶子还有空位，键按大小插进去，完事了。父节点不动、兄弟节点不动、叶子之间那根绳子也不动，整棵树的结构一个像素都没变。

```
叶子 [10 | 20]  ← 插入 35
叶子 [10 | 20 | 35]
```

就这样。真的就这样。

我猜大多数人对 B+ 树的印象全被「分裂」两个字占满了，以为插入必然伴随结构变动。实际跑一遍就知道：一棵有几十万个键的 B+ 树，插入一个键触发分裂的概率低得可怜。**分裂是例外，不是常态。**

先把"什么都不变"这件事刻进脑子里，后面的大动作才有分量——它是在告诉你，什么时候才值得动手。

---

## 三、叶子塞满了：键是「复制」上去的

现在叶子已经 3 个键（4 阶的上限），再插一个 `40`，它就装不下了。

处理办法是**一分为二**：左半边留在原节点，右半边搬去一个新兄弟节点。这很好理解，抽屉塞不下就腾一个出来。

真正的问题是：**父节点怎么知道该往哪个抽屉找？**

答案是——把右半边最小的那个键，**复制一份**送到父节点，当地址牌用。

```
叶子 [10 | 20 | 30]  ← 插入 40
        ↓
叶子 [10 | 20]   叶子 [30 | 40]
                    ↑
              30 复制一份给父节点
```

注意看，`30` 现在有两个身份：在叶子里它是真数据，在父节点里它只是一块路牌。**两个都存在，谁也不消失。**

这就是为什么我叫它「复制」而不是「移动」。这个区别不是文字游戏——叶子存的是真实数据行，你要是把它搬到父节点去，那这条记录就从数据层消失了，查询直接查不到。

用图书馆的话说：书架上多腾了一格，你在门口牌子上新钉了一块「30 号以后往右」，牌子上的 30 是从那本书的编号抄过来的，书还在架子上。

---

## 四、父节点也满了：这次键是真被搬走的

现在麻烦来了。如果父节点本身已经满了（3 个键 4 个孩子），再接收一个键就变成 4 个键 5 个孩子，也撑破了。

它得用同样的办法分裂。但这里有个**关键的不同**：

{{< svg "bplus-split-rules" "叶子分裂是复制，非叶分裂是上移——同样是分裂，键的去向完全不同" >}}

**非叶节点分裂，是正中间那个键被「抽走」交给上一层，自己不留。**

还是那张图右边：`[30 | 50 | 70 | 90]` 溢出，中间那个 `70` 被拿出来交给祖父节点，自己剩下 `[30 | 50]` 和 `[90]` 两个节点。注意 `70` 在这两个节点里**都不存在了**。

为啥这次不用复制？因为非叶节点存的本来就是路牌，路牌上的号码本来就是个副本。既然上一层已经有一块一模一样的牌子了，下面这块留着纯属占地方，抽走正好还能让两个新节点都松快一点。

一句话总结这个最容易被记反的点：

| | 叶子分裂 | 非叶分裂 |
| --- | --- | --- |
| 送给父节点的是 | 右半边最小键 | 正中间那个键 |
| 怎么送 | **复制**，原地保留 | **上移**，从子节点删除 |
| 分裂后 | 左右各 2 个键 | 左 2 键 3 指针，右 1 键 2 指针 |
| 为什么 | 叶子存真数据，不能搬走 | 非叶只是路牌，留两份没意义 |

> 复制还是上移，取决于这个键是不是"真货"。真货只能抄，路牌可以搬。

## 五、一路顶到根：树就这么长高了一层

分裂要是继续往上冒，冒到根了呢？

根没有父节点可以接手这个键了。这时候系统会**新建一个根**，把那个要上交的键放进去，原来的根变成它的左孩子，分裂出来的新节点变成右孩子。

树高就这么 +1 了。

**这是 B+ 树唯一的长高方式。** 不是往下长，是从根往上顶出来的。所以任何时刻，所有叶子都严格处在同一层——这也是为什么 B+ 树的查询代价稳得像块砖，永远不会出现「查这个键走 3 层、查那个键走 7 层」的情况。

顺便提一句复杂度：分裂只会沿着「根 → 目标叶子」这一条路径向上冒，兄弟子树完全不受影响。所以插入是 O(log n)，而且只有这条链上的节点会被改写。

## 七、核心代码就这几行

页面里跑的是个真的 4 阶 B+ 树，不是假的动画。核心逻辑抽出来就这么点（Java，可以直接跑）：

```java
/** 4 阶 B+ 树的节点：最多 3 个键、4 个孩子 */
static class Node {
    boolean leaf;
    List<Integer> keys = new ArrayList<>();
    List<Node> children = new ArrayList<>();
    Node prev, next;              // 叶子之间的双向链表

    Node(boolean leaf) { this.leaf = leaf; }
}

/** 分裂的产物：一个要上交的键 + 一个新兄弟 */
static class Split {
    final int upKey;
    final Node newNode;
    Split(int upKey, Node newNode) { this.upKey = upKey; this.newNode = newNode; }
}

private static final int MAX_KEYS = 3;

/** 往子树里插；返回 null 表示没分裂，否则把「新兄弟」往上交 */
private Split insert(Node node, int key) {
    if (node.leaf) {
        // 叶子：保持有序插进去
        int i = 0;
        while (i < node.keys.size() && node.keys.get(i) < key) i++;
        node.keys.add(i, key);
        return node.keys.size() > MAX_KEYS ? splitLeaf(node) : null;
    }

    // 非叶：先决定走哪个孩子。注意是 >= 才往右走
    int i = 0;
    while (i < node.keys.size() && key >= node.keys.get(i)) i++;
    Split sub = insert(node.children.get(i), key);
    if (sub == null) return null;

    // 孩子裂了，把这个键和新兄弟接过来
    node.keys.add(i, sub.upKey);
    node.children.add(i + 1, sub.newNode);   // 注意是 i + 1，不是 i
    return node.keys.size() > MAX_KEYS ? splitInternal(node) : null;
}

/** 叶子分裂：右半边最小键「复制」一份上去，自己留着 */
private Split splitLeaf(Node leaf) {
    int mid = (MAX_KEYS + 1) / 2;              // 4 个键 → 2 / 2
    Node right = new Node(true);
    right.keys.addAll(leaf.keys.subList(mid, leaf.keys.size()));
    leaf.keys.subList(mid, leaf.keys.size()).clear();

    // 维护叶子链表：把新节点接到后面去
    right.next = leaf.next;
    right.prev = leaf;
    if (right.next != null) right.next.prev = right;
    leaf.next = right;

    return new Split(right.keys.get(0), right);   // get，不是 remove —— 这就是「复制」
}

/** 非叶分裂：中间那个键「上移」出去，自己不留 */
private Split splitInternal(Node node) {
    int mid = (MAX_KEYS + 1) / 2;              // 4 个键 → 抽走索引 2
    int upKey = node.keys.remove(mid);         // remove，不是 get —— 这就是「上移」

    Node right = new Node(false);
    right.keys.addAll(node.keys.subList(mid, node.keys.size()));
    node.keys.subList(mid, node.keys.size()).clear();
    right.children.addAll(node.children.subList(mid + 1, node.children.size()));
    node.children.subList(mid + 1, node.children.size()).clear();

    return new Split(upKey, right);
}
```

代码里最能说明问题的就是那两个词：`splitLeaf` 里用的是 `get(0)`，`splitInternal` 里用的是 `remove(mid)`。**一个取出来看一眼，一个真拿走。** 整篇文章讲的东西，其实就压缩在这两个方法名的差别里。

还有个小坑顺手提醒：往 `children` 里插新节点时索引是 `i + 1`，不是 `i`。因为键插在第 `i` 位，意味着它右边多了一个孩子，那个新孩子自然排在第 `i + 1` 位。我第一次写的时候就是这儿写错了，跑了半天发现树长歪了。

## 写在最后

回头看看，其实整件事就四条规则：

1. 数据只往叶子里塞
2. 叶子装不下就分两半，右半边的最小键**复制**一份给父节点
3. 非叶装不下也分两半，但中间那个键是**搬走**的，不留
4. 一路顶到根，根裂了就长出新根，树高 +1

难的不是记住这四条，是**想明白第 2 条和第 3 条为什么不一样**。一旦你想通了「叶子存真数据、非叶只存路牌」这个前提，那两条规则就不是要背的东西了，而是唯一合理的做法。

做那个沙盒的时候我还顺手踩到几个有意思的点：InnoDB 的分裂点其实不是按键的数量对半分，而是按页内**字节数** 50% 来拆——因为 varchar、text 这类变长字段会让每个键占的字节差得很远，按个数分容易拆出个严重失衡的两半。这个细节面试提一句，一般挺加分。

以上是个人的一些理解，如果有哪里说得不对的地方也请大佬们指出。
