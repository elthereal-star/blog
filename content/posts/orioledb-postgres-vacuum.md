不知道做后端的朋友有没有过这种体验——某张表就这么几百万行数据，查询却莫名其妙越来越慢，`EXPLAIN` 一看索引也走了，执行计划挑不出毛病，最后查来查去发现是**表膨胀得像个气球**。

然后你半夜爬起来跑 `VACUUM FULL`，好家伙，锁表半小时，业务群里已经开始 @ 你了 (꒦ິ⌓꒦ີ)

**10 月 1 号，Supabase 把 OrioleDB 推到公测了。** 这个存储引擎的目标非常直接：**让 VACUUM 从你的运维日程里消失。**

官方在 TPC-C 基准上测出来的数字是 **1.8 倍吞吐**，而且是拿真实的事务型负载跑的。

今天咱就来盘一盘，VACUUM 这个从 Postgres 诞生就跟到现在的老家伙，到底为什么能"被干掉"，以及——**为什么我劝你先别急着上生产**。

---

## 先说清楚：VACUUM 到底在救什么火？

要理解 OrioleDB 想干什么，得先搞明白 Postgres 现在是怎么干活的。

Postgres 有个原则：**读的人可能还在读旧数据，所以不能把旧数据删掉。**

举个图书馆的例子哈。假设图书馆只有一本《MySQL 从入门到跑路》，你想借，但 A 同学正在看。管理员怎么办？总不能把书从 A 手里抢过来给你吧。

Postgres 的做法是：**你再进一本新的放架子上，A 同学手里那本旧的让他慢慢看完。**

这个策略本身没毛病，甚至很优雅——`UPDATE` 一条记录的时候，Postgres 不是原地改，而是**在表里写一个新版本**，原来那行原地不动，标记成"旧版本"。这样已经开始的读事务还能安心读旧数据，不用加锁，不用互相等待。

**但代价来了：那本"旧书"会一直躺在架子上。**

它已经没人要了，但表里还占着位置。这就是所谓的**死元组（dead tuple）**。

时间一长，问题就大了：

- 表文件越来越大，明明只有一百万行活数据，文件可能已经几 GB 了
- 查询要扫过大量已经死掉的页，白白浪费 IO
- 索引也跟着膨胀，缓存命中率一路下滑

**VACUUM 就是那个定期来清书架的图书管理员。** 它扫一遍表，把确认没人再读的旧版本回收掉，空间标成"可复用"。

听起来挺好？问题是这个管理员活儿很重：

| 麻烦 | 具体表现 |
| --- | --- |
| 争抢 IO | VACUUM 要全表扫，跑起来和业务抢磁盘带宽 |
| autovacuum 调不明白 | 调勤了影响性能，调懒了表膨胀，阈值还得按表调 |
| 锁 | `VACUUM FULL` 要拿排他锁，直接锁表；普通 VACUUM 虽然不锁，但也救不了已经膨胀的空间 |
| 杀了就白干 | VACUUM 干到一半被 kill（或者机器重启），之前扫的工作全废，还得重来 |

**更刺激的还在后面——事务 ID 回卷。**

Postgres 的事务 ID 是 32 位，也就是大约 42 亿个。每产生一个事务就消耗一个，用完了……它会绕回去从零开始。这时候数据库就分不清"这条记录是过去写的"还是"未来写的"了——**这是真正会导致数据丢失级别的故障**。

所以 Postgres 必须赶在回卷之前把老数据"冻结"掉。大概跑到 20 亿左右，它就开始疯狂告警；再往后要么拼命冻结，要么干脆**拒绝一切写入**保命。

这个坑不是理论上的。**2018 年 Sentry 就因为这个让整个主库停了写**——他们的数据库跑了太久没处理，XID 逼近临界值，最后只能靠停机来处理。业内因为回卷出事故的案例，一只手数不过来。

## OrioleDB 的三招

好，铺垫完了。OrioleDB 的思路是：**既然这些麻烦都是"把旧版本留在表里"带来的，那就别留在表里。**

它是 Postgres 的一个扩展，用的正是 Postgres 那个 `table access method` 框架——也就是说，**它是换存储引擎，不是另起一个数据库**。你的 SQL、JDBC 驱动、ORM、连接池全都不用动。

{{< svg "vacuum-vs-undo" "同样一次 UPDATE：heap 把旧版本留在表里，OrioleDB 把它推进 undo log" >}}

具体靠三招：

### 第一招：索引组织表，干脆不要 heap 了

传统 Postgres 是"heap + 索引"两层结构：数据存在 heap 里，索引里存的是指向 heap 的指针。**主键查一条数据，得先查索引，再回 heap 拿整行——两次 IO。**

OrioleDB 学的是 MySQL InnoDB 那套：**索引组织表（index-organized table）**，数据直接存在主键 B-tree 的叶子节点里。

主键查询少一次跳转，天然快一截。代价是这张表**必须有主键**——你没显式定义的话，它会偷偷用 `ctid` 给你造一个隐藏的。

顺带一提，它还把共享缓冲池那套 `buffer mapping` 干掉了：内存页和存储页直接链接，读页甚至不需要原子操作。这在几十上百核的机器上差别很明显——heap 那套在高并发下的锁争用是出了名的瓶颈。

### 第二招：undo log 接替"就地留旧版本"

这是最核心的一招。

前面说了，heap 的做法是"旧版本留在表里等 VACUUM"。OrioleDB 改成：**旧版本不进主存储，而是写进 undo log。**

用图书馆那个比喻：现在管理员学聪明了，**你借新版，旧版直接从架子上抽走，扔进后面的归档室**。架子上永远是当前有效的书，干干净净。

这个 undo log 有几个关键设计：

- **page-level 而不是 per-tuple**。一次操作产生的 undo 记录是按**页**记的，不是按行。好处是对一个页做什么修改（包括分裂、重排、压缩），都只需要应用一条 undo 记录，不用一行行走 undo 链。代价是这条记录会比较大（要存整页的旧版本），换来的是锁持有时间更短
- **它是环形 buffer，满了自动覆盖**。有两个池：系统级和普通数据块级，可以通过 `system_undo_circular_buffer_fraction`、`regular_block_undo_circular_buffer_fraction` 这两个参数调
- **理论上 99% 的场景不需要 VACUUM**。剩下那 1% 靠 `merge_pages` 兜底——那是**就地合并**，不是物理删除，比 VACUUM 轻得多

### 第三招：64 位事务 ID，回卷问题直接没了

既然事务信息不用像 heap 那样塞进每一行（heap 的每个元组都要存 xmin/xmax），就可以放开手脚用 **64 位事务 ID**。

为啥 heap 不敢用 64 位？因为这个 ID 存在每一行里，从 32 位改成 64 位**每行要多占 8 字节**。乘以几十亿行版本、再加上死元组，就是更多页、更大索引、更大 IO 压力。这个账算不过来。

OrioleDB 没有这个包袱，因为事务元数据走 undo log。**回卷问题从根上被消掉了**，不用再担心哪天半夜主库突然拒绝写入。

## 实际怎么用？

目前最省事的入口是 Supabase。他们在 Select 2026 大会上把它放进了公测。

建表就是普通 SQL，**不加任何特殊语法**：

```sql
-- 在 OrioleDB 实例里，默认就是 OrioleDB 存储
create table blog_post (
    id          int8        not null,
    title       text        not null,
    body        text        not null,
    author      text        not null,
    published_at timestamptz not null default CURRENT_TIMESTAMP,
    views       bigint      not null,
    primary key (id)
);

-- 索引也照常建，默认走原生 B-tree
create index blog_post_published_at on blog_post (published_at);

-- 想显式指定引擎也行，同一库里两种引擎的表能混用
create table log_archive (
    id   int8 not null,
    data jsonb,
    primary key (id)
) using orioledb;
```

最后那条 `using orioledb` 是重点：**同一个数据库里，heap 表和 OrioleDB 表可以并存**。你不用把整个库都迁过去，哪张表写得多、膨胀得厉害，就先拿哪张表试。

要知道某张表当前用的哪个引擎，`\d+` 就够了：

```sql
\d+ blog_post
-- 输出里会有一行：Access method: orioledb
```

（heap 表那里显示的是 `heap`。）

## 那几个数字，得掰开看

先看 Supabase 官方给的：在 8XL 实例（32 vCPU / 128 GiB 内存，**数据集比内存还大**）上跑 TPC-C 衍生负载，OrioleDB 大概 **112,800 TPM**，heap 是 **37,000~65,000 TPM**，**1.8 倍**。而且连接数往上加的时候差距还在扩大。

官方数字嘛，总归要打个折看。更有意思的是第三方实测（pgbench 造了约 500 万行，约 2 万次事务）：

| 指标 | heap | OrioleDB |
| --- | --- | --- |
| `VACUUM ANALYZE` 耗时 | 13.81 秒 | **6.01 秒** |
| 磁盘占用（同样 500 万活行） | 759 MB | **723 MB** |
| 累积的死元组数量 | 82,742 | 341,087 |

**注意最后一行**——OrioleDB 身上挂着**四倍于** heap 的死元组，磁盘占用反而还更小，VACUUM 还快一倍。

这组数据特别能说明问题：heap 的死元组是真的占地方、真的拖慢扫描；而 OrioleDB 的"死元组"已经在 undo log 里等着被覆写了，对主存储几乎没有影响。

**这就是"从根上解决"和"定期打扫"的区别。**

## 但是……先泼一盆冷水

好话说完，说限制。**这部分比前面重要，请务必看完再动手。**

**第一条，也是最要命的：只能在创建项目时选，中途加不了、也删不掉。**

Supabase 的文档写得很直白：OrioleDB 是在建项目的时候选的，**你没法给一个已有的项目加上它，选错了也没法改回来**。所以你的存量库想试，只能新建一个项目导数据过去。

**第二条，几个关键能力目前是缺的：**

- **没有 PITR（时间点恢复）**
- **不能把备份恢复到新项目**
- **pgvector 的 HNSW 索引走的是实验性 bridge**——你要做向量检索，这条路还没铺平

**第三条，生态工具链可能不认。**

OrioleDB 用的是**行级 WAL**，不是 Postgres 传统的页级 WAL。这意味着你熟悉的 `pg_basebackup`、`wal-g`、`pgBackRest` 这一票基于页 WAL 的工具，**不一定能直接兼容**。它还自带了一套独立的 checkpoint 控制文件机制。迁移方案得重新评估。

**第四条，undo buffer 是个双刃剑。**

那两个环形 buffer 的参数，调高了占内存，调低了——**数据就有被提前覆写的窗口期**。传统的 `shared_buffers = 25% RAM` 那套经验法则在这儿不完全适用，你得在自有基础设施上自己摸甜区。容器化环境（Supabase 的场景）会按比例缩放，但那是他们的活。

**最后，Supabase 自己说了：公测，没有 SLA，不推荐用于生产。**

所以我的判断很直接：**这是"下一个大版本的方向"，不是"今天该上的东西"。** 拿个写负载重的测试环境或者 side project 感受一下可以，正经业务先别动。

## 顺带说一句，同一场发布会还有两件事

Supabase 这次的 Select 2026 其实是打包发的，另外两个也值得知道一下：

**Multigres**——由 Vitess 团队做的 Postgres"操作系统"，把连接池和多节点故障转移做进去了。传统主从架构最尴尬的地方是：主库挂了、但数据还没同步到从库，那几条已提交的写入就丢了。Multigres 用一套共识协议，**保证故障转移时一条已提交的写都不丢**，秒级提升从库。目前私有 alpha，要申请。

**dbarena**——一个开源的 Postgres 基准测试站，**测试代码、数据集、绝对吞吐、每美元吞吐全都公开**，你可以自己复现结果。这个我觉得比数字本身更有价值：以后谁再拿"我们的性能是别人的 3 倍"这种话术，至少有个能对比的地方了。

再往外看一层，他们还宣布收购了 **Turso**（用 Rust 重写的 SQLite，支持并发写、一个服务扛几百万个库）。CEO 的说法是：**agent 正在成为数据库的主要客户**，Supabase 每周新建的库已经超过一百万个，大部分是 agent 建的。

把这几件事串起来看就清楚了——**数据库这一层正在为"海量的小库、随时创建随时销毁"重做一遍**。OrioleDB 解决的是"单个库扛得住多少"，Turso 解决的是"能不能便宜地开出几百万个库"。

## 写在最后

回头看，VACUUM 这个东西其实挺冤的。它不是什么设计失误，恰恰相反——**它是 Postgres 为了"读一致性"这个正确目标，不得不付出的运维代价**。三十年来大家一边享受着 MVCC 不用加锁读的好处，一边默默扛着 autovacuum 的调参地狱。

OrioleDB 的思路不是"把 VACUUM 优化得更好"，而是**"换个存储模型，让这个问题压根不存在"**。这种"绕过问题而不是解决它"的思路，我觉得比单纯把 VACUUM 调快一倍要值钱得多。

但它现在的状态也很典型：**架构上很有想法，工程上还没到能用的时候。** 没有 PITR、工具链不兼容、只能新建项目——这几条里随便踩中一条，都够让你的迁移计划黄掉。

所以我给的建议就一句话：**拿个 side project 玩，别碰生产。**

至于 VACUUM 会不会真的失业……我看短期内不会。但"VACUUM 是可以没有的"这件事被证明出来之后，Postgres 未来的存储层大概率会往这个方向走。三十年的老设计要换代了。

以上是个人的一些观察，如果有哪里说得不对的地方也请大佬们指出！
