## 项目要解决什么

校招和实习投递这件事，信息量比想象中大：投了哪些公司、每家到哪一轮、什么时候该催、最后哪些给了 Offer。

散在 Excel、记事本、聊天记录里的问题很明显：**状态更新不及时，进展全靠回忆。**

所以做了 offer-tracker：一个管理投递全流程的单体应用，包含公司库、投递看板、状态自由调整、面试轮次和数据统计。

技术选型没有惊喜，全是成熟组合：

| 层 | 选型 |
| --- | --- |
| 后端 | Java 21 + Spring Boot 3 + MyBatis-Plus |
| 数据库 | H2（默认）/ MySQL 8（`mysql` profile） |
| 迁移 | Flyway |
| 接口文档 | springdoc-openapi |
| 前端 | Vue 3 + Element Plus + Vite |
| 测试 | JUnit 5 + Testcontainers + Playwright |
| 构建/部署 | Maven + GitHub Actions + Docker |

选 H2 作为默认数据库是个有意的设计：**`java -jar` 双击就能跑，不需要装任何数据库。** 想上 MySQL 换个 profile 就行。

## 决定一：一条命令交付

`mvn package` 是这个项目唯一的交付入口，它会依次完成：

1. 自动下载项目专用的 Node.js 和 npm（不依赖本机 Node 版本）
2. 安装前端依赖
3. 跑前后端测试
4. 构建前端静态资源
5. 把静态资源打进 `BOOT-INF/classes/static`
6. 产出完整可运行的 JAR

结果就是 `java -jar target/offer-tracker-0.1.0.jar` 一个文件搞定，不需要「先起前端 dev server 再起后端」这种开发态拼装。

**为什么值得花这个力气？** 因为「在我电脑上能跑」和「交付一个能跑的东西」是两回事。构建步骤一旦只存在于我的终端历史里，它就随时会丢。

只有在「前端已经构建过、只想单独调后端」时才用 `-Dskip.frontend=true` 绕过。

## 决定二：统一响应结构

所有接口返回同一个信封：

```json
{ "code": 0, "message": "ok", "data": { } }
```

`code != 0` 表示业务失败，同时**配合正确的 HTTP 状态码**——不是所有错误都返回 200。

这么做的好处是前端只需要写一次拦截器：

```js
// 伪代码
if (res.data.code !== 0) {
  showError(res.data.message);
  return Promise.reject(res.data);
}
```

业务代码里不用再逐个判断响应形状。

## 决定三：状态可以自由调整，而不是强制流转

投递状态有七个：

```text
SAVED → APPLIED → WRITTEN_TEST → INTERVIEWING → OFFER
                                              ↘ REJECTED
                                              ↘ WITHDRAWN
```

我一开始想做一个严格的单向状态机，后来放弃了。**真实流程不是线性的**：

- 有公司直接约面，跳过笔试；
- 有的一开始没投（收藏着），后来才投；
- 有的挂在笔试但半年后又联系你复捞；
- 有的流程走完了又反悔，状态要退回去。

所以最终设计是 `PUT /api/applications/{id}/status` **允许任意合法状态之间的流转**，不校验「上一步是什么」。

这里的关键判断是：**状态不是流程控制，而是用户对现实的标注。** 系统不该比用户更懂发生了什么。

## 决定四：备份恢复要先预检

数据备份导出成 JSON，恢复的时候分两步走：

```text
POST /api/data/import/validate   → 预检，返回会不会冲突
POST /api/data/import            → 真正执行（追加 或 清空后恢复）
```

预检会检查：

- 公司、投递、面试之间的引用是否完整（有没有孤儿面试记录）
- 同一投递下是否存在重复轮次
- 主键与现有数据是否冲突

**为什么要多这一步？** 因为「恢复备份」是仅次于「删除」的危险操作，它可能把当前数据整个覆盖掉。让用户先看到「这次恢复会新增 12 条投递、覆盖 3 条、发现 1 处冲突」，比直接开干强太多。

另外 CSV 导出只用于表格分析，**完整恢复必须用 JSON**——CSV 天然丢失关联关系，用它恢复等于制造脏数据。

## 决定五：CI 里必须跑端到端

GitHub Actions 上跑四件事：

1. 前后端测试 + 完整 JAR 构建
2. **JAR 静态资源内容校验**（确认前端真的被打进去了，而不是构建成功但产物是空的）
3. Chromium 看板拖拽端到端测试
4. Docker 多阶段镜像构建

第 2 条是我被坑过之后加的：某次前端构建静默失败，`mvn package` 依然成功，产出的 JAR 里 `static/` 是空的，打开页面一片白。**构建成功 ≠ 产物正确**，所以加一道断言去检查产物内容。

第 3 条用的是 Playwright，它会在 `18080` 端口起一个独立的 JAR、用内存 H2 跑，所以**不会碰开发数据**。这点很重要，端到端测试污染本地数据是很难排查的问题。

如果本机已经有 Edge，可以跳过 Chromium 下载：

```powershell
$env:E2E_BROWSER_CHANNEL = 'msedge'
npm run test:e2e
```

## 决定六：做 Windows 便携版

这个功能看起来和「后端项目」没什么关系，但它是整个项目里我最满意的部分：

```powershell
.\packaging\package-windows.ps1
```

跑完得到 `dist/OfferTracker-Windows-x64-<version>.zip`，解压双击 `OfferTracker.exe` 就能用。程序会：

- 自带 Java 运行环境，**目标机器不需要装 JDK**
- 自动选择空闲端口，避免 8080 被占用
- 自动打开默认浏览器
- 通过系统托盘提供「打开」和「退出」
- 数据存在 `%LOCALAPPDATA%\OfferTracker\data`，不写安装目录

做这个的原因很简单：**我身边需要用这个工具的人，不会去装 JDK、配环境变量、敲 `java -jar`。** 一个真正能被使用的工具，门槛应该在「解压」这一层。

顺带一个副作用是好的：数据不写安装目录，意味着重装、换版本都不会丢数据。

## 还没做的

- [ ] 面试前提醒（定时任务 + 邮件/Webhook）
- [ ] 从招聘网站 URL 自动解析公司与岗位
- [ ] Excel 导入与逐行错误报告
- [ ] 多用户与登录认证（Spring Security + JWT）

其中**自动解析招聘 URL** 是投入产出比最高的：用户粘贴一个链接，自动填好公司、岗位、城市，能省掉大量手工输入。

## 小结

这个项目最大的收获不是写了多少接口，而是理解了一件事：

> **功能实现只是及格线，「敢交付」才是目标。**

围绕这个目标长出来的一堆东西——一条命令构建、统一响应、状态可回滚、恢复前预检、CI 校验产物、便携版打包——每一样单独看都不酷，但合起来决定了这个东西是「一个练习项目」还是「一个能给别人用的工具」。
