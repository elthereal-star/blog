## 为什么还要再造一个

下载文件夹是大多数人电脑里最乱的角落，同类工具也不少。我决定自己写，是因为它们有三个通病：

1. **闭源或者太重**，装完一堆依赖，还要常驻后台。
2. **不可撤销**。批量移动是个破坏性操作，但很多工具只给你一个「整理完成」的提示，出错了只能自己手动翻。
3. **规则不可配置**。真正的需求往往很具体——「PDF 归文档、截图归图片、剩下全丢其他」，这种规则应该写下来固定住。

所以目标定得很明确：**一个 jar 包 + 一份 YAML，就能把整理规则固化下来，并且永远可撤销。**

## 核心设计：撤销不是附加功能，是地基

几乎所有同类工具都把「撤销」放在 Roadmap 最后一行，我把它放在最前面。因为它会反过来决定其他所有设计。

### 用追加写的 JSONL 记录每一次移动

每次移动文件，都往 `.filetidy-history.jsonl` **追加**一行：

```json
{"batchId":"20260915-143022-7f3a","from":"C:/Users/me/Downloads/a.pdf","to":"C:/Users/me/Downloads/02-文档/a.pdf","ts":"2026-09-15T14:30:22+08:00"}
```

几个刻意的选择：

- **JSONL 而不是 JSON 数组。** 追加写不需要读全文改全文，中途崩溃也不会把整个历史文件写成半截。写坏了最多丢最后一行。
- **带 `batchId`。** 一次 `organize` 运行是一个批次，`undo` 按批次整体回滚，而不是「退回上一步」。用户的心智模型是「把刚才那次整理撤掉」，不是一个操作一个操作地退。
- **记录 `to` 而不是只记录规则。** 撤销时不需要重新跑一遍规则去推算目标位置——文件可能已经被改过名了，推算必然出错。直接记录事实。

于是 `undo` 的实现变得极其简单：读最后一批记录，**反向**把文件移回去，然后把这一批从历史里标记掉。

### 永不覆盖

目标位置已经有同名文件时，不覆盖、不报错，自动追加序号：

```text
报告.pdf → 报告 (1).pdf → 报告 (2).pdf
```

理由很直白：**整理文件这个动作应该是「无损」的。** 用户按了一次回车，不应该有任何数据丢失的可能性。宁可留下几个带序号的重复文件，也不能吃掉一个。

### 只扫描目录第一层

`organize` 只处理目标目录的直接子文件，**不递归**。

这个决定看起来偷懒，其实很关键：整理完的结构长这样——

```text
Downloads/
├── 01-图片/
├── 02-文档/
└── 99-其他/
```

如果递归扫描，第二次运行时那些已经归好类的文件会被重新匹配规则、再次移动，可能被挪到别的分类里，甚至产生 `01-图片/01-图片/a.jpg` 这种套娃。只扫一层，就等于把子目录声明为「已归档区」，天然幂等。

## watch 模式：为什么用全量重扫而不是增量事件

`--watch` 的直觉实现是监听文件系统事件，收到「新增文件」事件就处理那一个。

我最后没用这个方案，而是**每次事件触发后，重新扫一遍第一层**，做完差异对比再动手。

原因是浏览器的下载行为很坑：

- 下载大文件时会先创建 `.crdownload` / `.part` 临时文件，下载完再改名，触发多次事件。
- 分块下载会产生一连串大小变化的事件。
- 有些下载器会先写临时目录再移动到目标目录。

如果按事件处理，就会撞上「文件还没写完就被移走」的问题。全量重扫的代价是每次多扫几十个文件名（毫秒级），换来的是**天然规避重复事件和半截文件**。这笔账很划算。

## 规则配置

规则就是一份 YAML，按扩展名匹配，没命中的落在 `fallback`：

```yaml
rules:
  - name: images
    target: 01-图片
    extensions: [jpg, jpeg, png, gif, webp]
  - name: documents
    target: 02-文档
    extensions: [pdf, doc, docx, xls, xlsx, md]
fallback: 99-其他
skipHidden: true
```

用 YAML 而不是 JSON 或者命令行参数，是因为这份东西**用户会想改**，而且想加注释说明为什么这么分类。命令行参数做多条件就变成了灾难。

## `--dry-run` 是我自己用得最多的功能

```bash
java -jar target/filetidy.jar organize ~/Downloads --dry-run
```

先打印一份「即将发生的移动计划」，不动任何文件。规则改完先 dry-run 看一眼，确认了再真跑。

这个功能对 CLI 工具来说几乎是必需品——**破坏性操作必须先能预演。**

## 技术栈上的两个小决定

**picocli 而不是手写参数解析。** 子命令、长短选项、帮助信息全自动生成，`--help` 的输出质量直接决定工具好不好用。

**Java 21 但保持零运行时依赖。** 除了 picocli 和 YAML 解析，没引入别的。目标是发布一个十几 MB 的单独 jar，双击就能用。

## 小结

这个项目的收获是：**当一个工具具备破坏性时，把「可撤销」当作第一需求而不是附加功能，架构会自然地往正确的方向长。**

因为要能撤销，所以必须记录事实而不是推算；
因为要记录事实，所以引入了批次概念；
因为有批次，所以「撤销」有了明确的语义边界。

反过来先做功能再加撤销，通常只能做出一个「撤销最近一步」的半成品。
