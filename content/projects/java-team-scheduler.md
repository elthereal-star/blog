## 它是什么

一个用 Java SE 实现的简易开发团队调度系统：管理员工信息、分配开发设备、按规则组建团队，并处理各种非法操作。

定位是**面向对象的综合练习**，代码不依赖任何框架，把 Java 基础里的核心语法一次性用起来。

- **源码**：https://github.com/elthereal-star/-Java-
- **状态**：练习项目

## 建模的对象

**员工体系**（继承 + 多态的核心练习）：

```text
Employee（抽象基类）
├── Programmer   程序员
├── Designer     设计师
└── ArchiTect     架构师（同时具备程序员和设计师的技能）
```

架构师这个类的存在是刻意的设计：它天然需要「多继承」的语义，而 Java 不支持类多继承，只能用**接口**来实现。这就是接口在这个项目里的意义。

**设备体系**（接口实现的练习）：

```text
Equipment（接口）
├── PC           台式机
├── NoteBook     笔记本
└── Printer      打印机
```

每个设备类自己实现「设备描述」的行为，员工持有的是 `Equipment` 接口引用——运行时按实际类型输出不同结果，这是多态最直观的体现。

**状态用枚举而不是魔法数字：**

```java
public enum Status {
    FREE, BUSY, VOCATION;   // 空闲 / 已加入团队 / 休假
}
```

## 分层结构

```text
├── Employee / Programmer / Designer / ArchiTect   领域模型
├── Equipment / PC / NoteBook / Printer            设备接口与实现
├── Status                                          状态枚举
├── NameListService                                 员工数据服务（内置员工列表 + 按 ID 查询）
├── TeamService                                     团队管理服务（添加/删除成员、校验规则）
├── TeamView                                        控制台交互界面
├── TeamException                                   自定义业务异常
├── TSUtility                                       控制台输入输出工具
└── Data                                            数据常量
```

**View 和 Service 分离**是这个项目最值得练的部分：`TeamView` 只负责和控制台打交道，所有业务规则都在 `TeamService` 里。用户输入非法数据时，Service 抛出自定义异常，View 捕获后打印友好提示，而不是让程序直接崩掉。

## 练习到的语法点

| 语法点 | 在哪里用到 |
| --- | --- |
| 抽象类与抽象方法 | `Employee` 定义员工通用属性与抽象行为 |
| 继承与方法重写 | 三类员工各自重写展示逻辑 |
| 接口与实现 | 设备体系；架构师通过接口获得「多继承」能力 |
| 多态 | 用父类/接口引用指代具体子类对象 |
| 枚举 | `Status` 表示员工状态 |
| 数组与集合 | 员工列表、团队成员数组的动态增删 |
| 自定义异常 | `TeamException` 表达「团队已满」「成员重复」「员工不存在」等业务错误 |
| 封装 | 私有字段 + getter/setter，成员数量受限时用常量约束 |

## 核心业务规则

- 团队最多 **5 人**，超员抛出异常
- 同一员工不允许重复加入团队
- 只有 `FREE` 状态的员工能被加入团队，加入后状态变为 `BUSY`
- 删除成员后状态恢复为 `FREE`
- 只有程序员、设计师、架构师可以加入开发团队（其他职位不允许）

这些规则全部在 `TeamService` 里集中校验，`TeamView` 拿到的永远是合法结果——**校验只有一处**，这是分层最实际的收益。

## 运行

纯 Java SE 项目，无外部依赖：

```bash
javac *.java
java NameListTest
```

按控制台菜单提示输入数字选择操作。

## 后记

这个项目之后，我对「什么时候该用接口、什么时候用抽象类」这个问题才算真的想清楚：

- **抽象类**表达「是什么」——程序员**是**一种员工，共享姓名、年龄、薪资这些状态。
- **接口**表达「能做什么」——笔记本**能**作为一个开发设备，但它并不「是」某类设备的子集。

架构师同时具备两种技能，如果硬用继承就会撞上「Java 不支持多继承」这堵墙，而换成一个能力接口就自然解决了。
